# incu-qq-bot

QQ 群客服机器人：官方 SDK 收 `@机器人` 消息（含被引用的消息与图片），用 OAI 兼容模型 + 知识库作答；答不上来的转交到飞书反馈群提醒人工。

**全程无公网暴露**：QQ 与飞书都走官方 WebSocket 长连接（飞书侧额外用 REST 发消息），进程不监听任何端口。

## 架构

```
QQ 群（用户群）                                飞书（反馈群）
  用户 @机器人 + 可选引用/图片                   管理员 @机器人
        │                                            │
        ▼                                            ▼
  @tencent-connect/qqbot-nodejs（WS 长连接）   知识库管理菜单（WS 长连接）
        │  中间件：去重 → 记到达 → 去 @标记 → 必须@ → 引用解析
        ▼
  ┌──────────────────────────────────────────────┐
  │ 一次模型调用 = 静态前缀 + 多轮历史 + 本轮提问    │
  │   [system]    规则 + 知识库（逐字节稳定）       │
  │   [user]      [16:04] 用户A: … + 当时的图片    │
  │   [assistant] 上一轮的答复                    │
  │   [user]      本次提问 + 图片(data URL)      │
  └──────────────────────────────────────────────┘
        │
        ├── 知识库命中「可直接回复」→ 被动回复用户
        └── 需转交 → 调 forward_feedback 工具
                        │
                        ├── 回复用户「已转交，正在处理中」
                        └── 飞书 REST 推送提醒卡片 ──► 反馈群

  知识库 = kb/kb.yaml（正式库：人改文件 + 发版，或群里的「正式知识库」菜单改 + git 提交）
         + kb/kb.feishu.yaml（飞书菜单写入，改完即热重载，不用 deploy）
  数据落盘：data/forwards-YYYY-MM.jsonl（转交记录，按月切分，保留 30 天）
```

## 快速开始

### 1. 填凭据

复制 `.env.example` 为 `.env`（仓库里已给好 `.env`，内容一致），把 `PASTE_` 占位符换成真实值。程序只列出缺哪些变量，永远不会打印凭据内容。

`.env` 的值也可以写成 1Password 引用（`LARK_APP_SECRET=op://私有/飞书机器人/app-secret`）：这种写法用 `npm run dev:op` / `npm run start:op` 启动，会经 `op run` 就地解析（需要本机装好 1Password CLI 并 `op signin`）。普通的 `npm run dev` / `npm start` 直接读 `.env` 明文，不依赖 op cli。`./deploy.sh` 上传前也会用 `op inject` 解析——**只有解析后的明文上路**，解析失败或解析后仍有 `op://` 残留则拒绝上传，且值只走 SSH 的 stdin、不进命令行参数。

```bash
# 先不填 QQ_GROUP_OPENID 也能跑：机器人会把看到的群 openid 打进日志
grep "收到群消息" <日志>   # 复制 group=oc... / group=... 那个值填回去
```

### 2. 本地运行

```bash
fnm use 24        # 需要 Node >= 24
npm install
npm run smoke     # 离线自检（不需要凭据）
npm run dev       # 开发模式，改代码自动重启（读 .env 明文）
npm run dev:op    # 同上，但用 1Password 解析 .env 里的 op:// 引用
```

### 3. 服务器运行（Docker）

```bash
docker compose up -d --build
docker compose logs -f      # 看日志
docker compose restart      # 改完 kb/kb.yaml 后重启生效
```

`docker-compose.yml` 里没有 `ports:`，只走出站连接；内存上限 512MB，并关掉了全部 capability
与提权（`cap_drop: ALL` + `no-new-privileges`）。
`kb/` 是**可写**挂载——飞书群里的管理菜单要往 `kb/kb.feishu.yaml` 追加补充知识。
`kb/kb.yaml`（正式知识库）也能在群里改，但走的是主菜单里那个**红色危险入口**：
每步二次确认 + 填提交说明，删掉的进 `kb/kb.trash.yaml`。

**容器里不跑 git**：改完只往 `data/kb-commit-request.txt` 写一行提交说明，由宿主的
`scripts/kb-commit.sh`（cron / systemd timer 触发）在仓库里 `git add` + `commit` + `push`。
容器因此不挂 `.git`、不需要 git 二进制、也拿不到推送凭据——**这是刻意的**：
容器可写 `.git` 就等于能用 `hooks` / `core.sshCommand` 在宿主上执行代码，所以**绝不要把宿主的
`.git` 挂进容器**。脚本的安装与 `KB_*` 变量见下文「正式知识库（kb.yaml）：红色危险入口」。

如果本机是 arm64 而服务器是 x86_64（或者服务器内存很小、不适合跑 `npm ci` + `tsc`），用 `deploy.sh`：它在本机交叉编译出目标架构的镜像、连代码一起推上去，服务器只负责 `docker load` 和 `up`，全程不构建。整个流程只开两条 SSH 连接（每条都要按一次硬件密钥的指纹，所以刻意压到最少）。

> `deploy.sh` **不在仓库里**：脚本里写着服务器地址与远程目录，早已加进 `.gitignore`（历史上那份也已从所有提交里清掉）。它只存在于部署者的本机与服务器上，新克隆的人要按自己的机器写一份：`SERVER` / `REMOTE_DIR` 可用环境变量覆盖，其余是 `docker buildx` + `ssh` + `docker load` 的常规流程。

```bash
./deploy.sh            # 全量：构建 → 上传 → 重建容器 → 自检
./deploy.sh --kb       # 只同步除 kb.yaml 外的 kb/ 并重启（1 条连接、几秒）
./deploy.sh --feishu   # 只更新知识库，且连 kb.feishu.yaml 一起推（线上原有那份先备份）
./deploy.sh --pull     # 反向：把服务器上 kb/*.yaml 全部拉回本地并覆盖（以云上为准）
./deploy.sh --no-build # 跳过构建与上传，只同步代码并重建容器
./deploy.sh --logs     # 部署完直接跟日志
```

知识库是启动时读进内存的，所以改 `kb/kb.yaml` 后要重启容器才会生效（走菜单改的话会**就地热重载**，不用重启）；
日志里「知识库已加载：kb-<hash>」的 hash 是内容哈希，变了就说明新文件生效了。

> `kb/kb.feishu.yaml`（飞书补充知识）**不走 deploy**：容器里改完就地热重载，几秒生效。
> `deploy.sh` 的 tar 也刻意排除了这个文件——它是**服务器上的运行期状态**，不能被本机的试验内容覆盖。
> 两个例外都有独立开关：`--pull` 把它**拉回来**（云上那份才是最新的），`--feishu` 显式把它**推上去**
> （推送前会把线上原有那份备份进 `data/kb-feishu-snapshots/`，和程序自己留的快照同一套命名与保留策略）。
>
> `kb/kb.yaml` 与 `kb/kb.trash.yaml` 同理**永远不推**：正式知识库由「正式知识库」菜单在服务器上直接改，
> 由宿主的 `scripts/kb-commit.sh` 在仓库里提交、推送，属于运行期数据。要把它同步回本机就
> `./deploy.sh --pull` 或直接 `git pull`。

它不会在服务器上执行 `docker compose build`，所以那台机器多小都能跑；但这也意味着改了 `src/` 之后必须在**本机**重新部署，服务器上那份源码只是留档。

## 需要开通的权限

### QQ 开放平台（[q.qq.com](https://q.qq.com)）

1. 创建机器人应用，在「开发设置」拿到 **AppID / AppSecret**。
2. 群聊能力开箱即用，**不需要**申请全量消息、**不需要** markdown 报备、**不需要**配置回调地址（本机器人用 WebSocket 长连接）。
3. 把机器人拉进用户群。
4. 只有 `@机器人` 的消息会到达机器人，引用消息的内容会随事件一起送达（这是官方支持的能力）。

### 飞书（[open.feishu.cn](https://open.feishu.cn) → 开发者后台）

1. **创建企业自建应用**，拿到 **AppID / AppSecret**。
2. 「添加应用能力」→ 开启 **机器人**。
3. 「权限管理」开通这几个权限：
   - `im:message:send_as_bot` —— 以应用身份发消息（推送转交卡片、回知识库卡片）
   - `im:chat:readonly` —— 获取机器人所在的群列表（启动时自动识别反馈群、读群消息形式）
   - `im:message.group_at_msg:readonly` —— **只收「用户 @ 机器人」的消息**。这是这一组里最窄的一个；
     **不要**申请 `im:message.group_msg`（获取群组中所有消息，属于敏感权限），机器人不需要看群里其它聊天。
   - `card.action.trigger` 的权限要求是「暂无」，不用额外申请。
4. 「事件与回调」→ **两处订阅方式都选「使用长连接」**（不需要公网地址、不需要内网穿透）：
   - 「事件订阅」添加 `im.message.receive_v1`（接收消息）
   - 「回调订阅」添加 `card.action.trigger`（卡片回传交互）
5. 「版本管理与发布」创建版本并发布（企业自建应用按你的组织流程走审批）。
6. 把机器人拉进**反馈群**。

> 不做第 4 步也能跑：转交提醒照常工作，只是「@机器人 弹知识库菜单」不会有反应（长连接收不到事件）。
> 把 `KB_ADMIN_ENABLED=false` 可以彻底关掉这条链路。

## 知识库

知识库分两层，编译进同一个 system prompt：

| | 谁维护 | 内容来自 | 生效方式 |
|---|---|---|---|
| **正式知识库** `kb/kb.yaml` | 人改文件 + 发版，或「正式知识库」菜单（二次确认 + git 提交） | 随镜像走，运行期可改 | 重启进程；走菜单改则**即时热重载** |
| **飞书补充知识** `kb/kb.feishu.yaml` | 群里的管理菜单 | 运行期写入服务器 | **即时热重载，不用 deploy** |

两层的 `id` **必须全局唯一**（撞车直接拒绝启动/拒绝写入），因为 id 是日志、审计和「按 id 删一条」的锚点。

### 正式知识库：编辑 `kb/kb.yaml`

手工改文件后重启进程生效，并让模型缓存按设计失效一次。也可以在反馈群里走「正式知识库」菜单改
（见下文「正式知识库（kb.yaml）：红色危险入口」），那条路会即时热重载、并自动 `git commit`。

```yaml
entries:
  - id: reset-password          # 唯一 id
    title: 忘记密码 / 无法登录     # 给模型看的条目标题
    keywords: [密码, 忘记密码]    # 触发关键词
    route: answer               # answer=可直接回复 | forward=需转交人工 | answer_and_forward=先回复再转交
    answer: |                   # route=answer 时必须写
      请在登录页点击「忘记密码」……
  - id: billing-refund
    title: 退款 / 订单异常
    keywords: [退款, 订单]
    route: forward
    forward_hint: |             # 建议写：告诉模型转交时要带上什么信息
      需要用户提供：下单账号、订单号、支付截图。
```

规模建议 2000 字以内（约 3k token）。超过 8000 字符启动时会告警。

### 变量：同一段文本只写一处

顶层 `variables` 里定义文本片段，条目里用 `{{名称}}` 引用（名称只能用字母、数字、下划线、短横线）。变量可以引用别的变量，加载时按依赖展开：

```yaml
variables:
  # 当前发布版本（加引号，见下）
  latest-version: "5.16.0"
  # 应用下载站 + 群文件兜底
  app-download: https://incu.ncu.edu.cn/
  app-package-hint: 群文件内也有最新版安装包
  # 教务系统入口与咨询电话
  jwpt: https://jwpt.ncu.edu.cn/jsxsd/sso.jsp
  jwpt-phone: "0791-83969101"
  jwpt-help: 如果对教务系统有疑问，请咨询{{jwpt-phone}}。

entries:
  - id: download
    title: 下载南大家园
    keywords: [下载, 更新]
    route: answer
    answer: |
      请在 {{app-download}} 下载最新版南大家园（当前版本 {{latest-version}}），{{app-package-hint}}
```

- 变量在**启动加载时**展开，编译进 system prompt 的仍是静态文本，不影响前缀缓存；改变量值等于改正文，会让缓存按设计失效一次。
- `variables` 本身不会进入 system prompt。
- 版本号、电话、编号这类值**要加引号**。不加引号的 `5.0` 会被 YAML 当成数字 `5`，`0791` 会变成 `791`——丢位是静默的，所以加载器见到非字符串的值会直接报错让你补引号。
- 未定义变量、循环引用、名字写错（例如写成 `{{版本号}}`）、变量值不是字符串，都会**在启动时报错并拒绝启动**，指出是哪个变量——不会把 `{{...}}` 或错值发给同学。

> 为什么不用 YAML 锚点：锚点只能整体替换一个节点，没法把一段文本嵌进句子中间。YAML 规范本身没有字符串插值，所以这层由加载器（`src/kb/kb.ts`）做。

三种处理方式：

- `answer`：直接回复用户，不建工单；
- `forward`：只转交人工；
- `answer_and_forward`：**先回复用户，同时转交人工**——适合「用户能自助办、但可能需要人工兜底」的场景（例如修改手机号：旧号还能用就自助改，不能用了得人工处理）。这类条目每次命中都会同时给用户答复并建一张转交卡片。

### 飞书补充知识：在群里 @机器人 就能加，不用 deploy

给同学临时的、来不及发版的知识，走这条路：**在反馈群里 @机器人**，机器人回一张主菜单卡片，点按钮操作，改完立刻生效（不重启、不重新部署）。

```
@机器人
  └─ 知识库管理（主菜单卡片，平铺在群消息里）
      ├─ 新增条目       → 两步向导（进话题）→ 「已新增」卡片（带「删除这一条」）
      ├─ 查看飞书补充知识 → 列表卡片（每条一个折叠面板，默认收起，每条自带「删除」）
      └─ 飞书补充知识开关 → 开 / 关整层飞书补充知识
```

「➕ 新增条目」是一个**两步向导**，第二屏只显示这次真正要填的那个输入框：

```
（1/2）id / 标题 / 关键词 / 处理方式下拉   [下一步]
   ↓ 点「下一步」（表单提交按钮 → 带 form_value）
（2/2）顶部用纯字符串回显上一步四项
       处理方式=可直接回复            → 只出「答案」
       处理方式=需转交人工            → 只出「转交说明」
       处理方式=先回复用户同时转交人工 → 两个都出
       [提交] [上一步]
```

为什么能这样（也是为什么值不会丢）：

- 卡片 JSON 是**静态一次渲染**的，飞书**没有条件显隐**，也没法让客户端自己留着未提交的输入。
  所以「上一步填的还在」靠两件事配合：**每一步的按钮都是表单里的提交按钮**
  （只有提交按钮的回调才带 `action.form_value`），以及服务端渲染下一屏时用
  `input.default_value` / `select_static.initial_option` 把值回填回去。
- 当前这一屏表单里没有的字段（例如第二屏不显示 id/标题），由**按钮的签名回传值**带着走——
  全程无服务端状态，来回切多少次都不会错，第二条也在内（退回第一步再点「下一步」，
  第二屏敲了一半的那段还在）。
- 因此**第二屏的输入框故意不设 `required`**：`required` 是前端拦截，一旦设上，
  用户点「上一步」会先被「有必填项未填写」挡住、带不走已写内容。第二屏的校验改在服务端做，
  失败时**只弹 toast、不更新卡片**，用户填的字原地保留。第一屏的四个字段仍然带 `required`
  （前端省一次往返），服务端也会再验一遍。
- 回退按钮值里带的是**签名**后的草稿，伪造不了；`op` 也用同一套 HMAC 保护。

**所有后续卡片都收在主菜单那条消息的话题里**（`reply_in_thread: true`），群里只多一行「N 条回复」，不会刷屏。
普通群就支持「对一条消息创建话题」，不需要把群改成话题群；万一某个群不支持，会自动降级为直接发在群里并记一条 warn。

它是怎么保证安全的：

- **入口只认白名单**：`LARK_ADMIN_OPEN_IDS`（逗号分隔 open_id），**默认空 = 谁都操作不了**。
  非白名单的人 @机器人 只会被静默忽略（日志里留下 open_id，复制进 `.env` 即可授权）；
  非白名单的人点卡片只会收到一个「你不是知识库管理员」的提示。
  填 `*` = **反馈群里所有人都能增删**。这一条**必须**同时设置 `LARK_FEEDBACK_CHAT_ID`：
  不显式指定群的话群是启动时自动认出来的，通配就等于把知识库开放给了意料之外的人。
  少配一样就不生效、只在启动日志里留一条 warn（fail closed）。
- **只有这个群能操作**：回调里的 `open_chat_id` 必须等于机器人的反馈群，避免卡片被转发到别处还能用。
- **回传数据带签名**：按钮带的是 `{op, id, added_at, sig}`，`sig` 是 `HMAC-SHA256(LARK_APP_SECRET, 其余字段)`。
  伪造的卡片或者改过字段的卡片一律拒绝（验签不过只弹一个 toast，什么都不做）。
- **写盘前先试编译**：用**和启动时同一个** `compileKnowledgeBase` 跑一遍候选内容，成功才落盘。
  所以「飞书加得进去、重启却起不来」不可能发生；`id` 与正式知识库撞车、变量引用不存在、
  总量超限这些都在这一步被挡下，卡片上直接显示原因。
- **补充层改不坏正式库**：飞书补充层这条卡片路径只认 `KB_FEISHU_PATH` 这一个文件，`kb/kb.yaml` 不在它的管辖内。
- **删除分两条路**：
  - 「已新增」卡片上的**删除这一条**是"撤销"，只在 24 小时内有效（`KB_DELETE_WINDOW_HOURS`），
    只按 id 严格相等匹配，还要求卡片带的时间与文件里的 `added_at` 完全一致；
    手工塞进文件的条目不受这条路径管辖。
  - 列表卡片里每条自带的**删除**没有时间窗口——入口本身就是"查看"，删除是明确意图，
    由飞书客户端的原生二次确认弹窗兜一道。
  - 两条路都是**先写回收站、再改补充层**；写回收站失败就整个不删（宁可删不掉，不能删丢了）。
- **删掉的进回收站，不会自动恢复**：`kb/kb.feishu.trash.yaml`（`KB_FEISHU_TRASH_PATH`），
  只增不改，程序没有任何读回入口。记录里的 id 是 `原 id + 短 uuid`（如 `feishu-jwpt_b29c894a`），
  这样同一条被反复删除也不会在归档里撞车。要恢复就手工搬回 `kb.feishu.yaml`、
  把 `_<uuid>` 去掉，之后再想删走列表里那条路。
- **落盘是原子的**：先留快照 → 临时文件 + rename。快照在 `data/kb-feishu-snapshots/`（保留最近 30 份）。
- **全程留痕**：谁、什么时候、加了/删了哪一条，写进 `data/kb-feishu-audit-YYYY-MM.jsonl`（受保留策略清理）。

规模闸门：单条答案 ≤1000 字（飞书输入框的硬上限就是 1000），飞书层编译后 ≤`KB_FEISHU_MAX_CHARS`（默认 2000），
合并后的 system prompt ≤`KB_MAX_PROMPT_CHARS`（默认 8000），超了直接拒绝写入并在卡片上说明。

> 想给某一条「转正」：用红色菜单「正式知识库 → 新增条目」把它写进 `kb/kb.yaml`，再从飞书层删掉同名那条
> （`id` 不能两处同时存在）。也可以老办法：`./deploy.sh --pull` 拉回 `kb/*.yaml`、手工复制进 `kb.yaml`。
> `added_by` 记着是谁加的，方便去确认。

**为什么飞书层追加在基线后面**：提示词缓存按字节前缀匹配。飞书层永远排在末尾，
所以同学在飞书里频繁增删时，基线段仍然逐字节稳定、缓存照旧命中；
基线段的「共 N 条」也只数基线条目，不会被飞书的增删带偏。

**为什么用卡片 JSON 2.0**：表单容器、多行输入框、下拉选择都要 2.0，而且飞书明确
「2.0 的卡片不能更新成 1.0」（错误码 200830）。转交提醒那套卡片是 1.0，两套各自独立、互不更新。

### 正式知识库（kb.yaml）：红色危险入口

临时知识走上面的补充层；**要改正式知识库**（`kb/kb.yaml`，随仓库发布的那份）就走主菜单底部的
红色按钮「正式知识库（kb.yaml）」。飞书群是可信的，所以这里不再限制「只能改补充层」，
但每一笔改动都做了更重的兜底：

```
知识库管理（主菜单）
  └─ 正式知识库（kb.yaml）        ← 红色 danger 按钮
      ├─ 新增条目   → 三步向导（第 3 屏确认 + 填提交说明）
      └─ 查看条目   → 列表卡片（每条一个折叠面板，面板里带「删除」）
                        └─ 点「删除」→ 另发一张确认卡片（填提交说明）→ 确认才删
```

- **二次确认是硬性的**：新增在第二步「提交」之后**先出一张确认页**，把完整条目回显出来，
  再要求填写**提交说明**；删除点下去**不会直接删**，而是发一张确认卡。两张确认卡上的
  「确认写入 / 确认删除」都是**表单提交按钮**，提交说明（空的不放行）随 `form_value` 上来。
- **每次都留 git 记录**：提交信息由服务端拼成 `chore(kb): <你填的说明>`，写进
  `data/kb-commit-request.txt`；**容器不跑 git**，由宿主的 `scripts/kb-commit.sh` 在仓库里
  `git add -- kb/kb.yaml` + `commit` + `push`。宿主侧要装一次定时器（cron 或 systemd timer 都行，
  一分钟一次足够）：

  ```bash
  # crontab -e（跑在拥有部署 key 的那台机器 / 那个账号上）
  * * * * * /path/to/repo/scripts/kb-commit.sh >> /var/log/kb-commit.log 2>&1
  ```

  脚本读这些环境变量（都有默认值）：`KB_REPO`（仓库根）、`KB_FILE`（默认 `kb/kb.yaml`）、
  `KB_GIT_REMOTE`（默认 `origin`）、`KB_GIT_PUSH`（**默认 true**，设 false 只提交不推送）、
  `KB_GIT_AUTHOR_NAME` / `KB_GIT_AUTHOR_EMAIL`。它只提交请求里约定的那一个文件、只接受
  `chore(kb): ` 前缀的单行说明，并且拒绝软链等非普通文件（容器对 `data/` 有写权限，
  宿主这一侧必须自己防）。`KB_GIT_ENABLED=false` 则连请求文件都不写。
  **提交失败不回滚**：文件已经写盘并生效，卡片会带一句提示，日志与审计里也记着原因，
  事后手工补一次提交即可。
- **改文档而不是重新渲染**：kb.yaml 里的人工注释、变量表都靠 `yaml` 的 `parseDocument` 原样保留，
  卡片只会往 `entries` 里增删一个节点，不会把整份文件重排。
- **删除进回收站**：`kb/kb.trash.yaml`（`KB_TRASH_PATH`），记录里的 id 是 `原 id + 短 uuid`。
  程序不自动恢复；要恢复就手工搬回 `kb/kb.yaml` 并去掉后缀。**所有条目都可删**（不区分手工/卡片添加）。
- **另有快照与审计**：写入前留一份 `data/kb-snapshots/*.yaml`（最近 30 份，git 之外的兜底）；
  谁、何时、增删了哪一条写进 `data/kb-audit-YYYY-MM.jsonl`（受保留策略清理）。
- **写盘前照样试编译**：id 撞车、变量没定义、删到一条不剩、system prompt 超 `KB_MAX_PROMPT_CHARS`
  都在这一步拦下，卡片上直接显示原因。

> 这一层和补充层的 `id` 必须全局唯一，两处不能同时存在；从补充层「转正」进正式库时，
> 先在红色菜单里新增、再回补充层把同名那条删掉即可（不用再登服务器改文件）。

## 限额与截断

| 环节 | 默认值 | 环境变量 |
|---|---|---|
| 用户单条提问 | 超过 4000 字符截断并标注 | `QUESTION_MAX_CHARS` |
| 上下文整段 | 超过 3000 字符时保留最新的部分 | `CONTEXT_MAX_CHARS` |
| 上下文单条消息 | 超过 600 字符单独截断（防一条超长粘贴挤掉其他） | `CONTEXT_MESSAGE_MAX_CHARS` |
| 回复发送 | 每段 ≤1600 字符、最多 3 段，超出截断 | `REPLY_MAX_CHUNKS` |
| 分钟级 | 单用户 6 条/分钟、单群 40 条/分钟 | `RATE_LIMIT_PER_MINUTE` / `RATE_LIMIT_PER_GROUP_PER_MINUTE` |
| 每日 | 单用户 10 条/日、全机器人 100 条/日 | `REPLY_LIMIT_PER_USER_PER_DAY` / `REPLY_LIMIT_GLOBAL_PER_DAY` |
| 转交 | 单用户 5 次/小时（计入上面同一份每日额度） | `FORWARD_LIMIT_PER_HOUR` |

- 计数按**东八区自然日**统计，落盘 `data/limits.json`，重启不清零；跨日自动重置并把前一天的用量归档为 `limits.YYYY-MM-DD.json`。
- 命中限额时只回一句提示，且**同一用户每分钟最多提示一次**（避免提示本身刷屏），不再调用模型。
- **豁免名单**：`PRIVILEGED_USERS`（逗号分隔 openid）里的用户不受分钟级、群级、转交每小时的限制，每日额度用 `PRIVILEGED_LIMIT_PER_DAY`（默认 100）。全局限额对他们仍然生效。
- 转交不单设每日上限，它和普通回复共用同一份「用户每日额度」。

## 数据文件与保留

| 文件 | 内容 | 切分方式 | 保留 |
|---|---|---|---|
| `data/limits.json` | 当日配额（openid → 次数、全局次数、已计过额度的图片 URL） | 单文件，跨日重置 | 常驻 |
| `data/limits.YYYY-MM-DD.json` | 每天的用量归档 | 每天一份 | 30 天 |
| `data/forwards-YYYY-MM.jsonl` | 转交留档（问题、详情、话题、飞书消息 id） | 按月切分 | 30 天 |
| `data/raw-events.<时间戳>.jsonl` | debug 原始事件转储 | 每次调试会话一份 | 30 天 |
| `data/kb-feishu-audit-YYYY-MM.jsonl` | 飞书知识库操作留档（谁、何时、加了/删了哪一条） | 按月切分 | 30 天 |
| `data/kb-feishu-snapshots/*.yaml` | 飞书补充知识每次写入前的快照（回滚用） | 每次写入一份 | 最近 30 份 |
| `data/kb-audit-YYYY-MM.jsonl` | 正式知识库（kb.yaml）卡片操作留档 | 按月切分 | 30 天 |
| `data/kb-snapshots/*.yaml` | 正式知识库每次写入前的快照（git 之外的兜底） | 每次写入一份 | 最近 30 份 |
| `kb/kb.feishu.trash.yaml` | 删掉的飞书补充条目归档（只增不改，程序不读，**不参与自动清理**） | 单文件 | 手动 |
| `kb/kb.trash.yaml` | 删掉的正式条目归档（只增不改，程序不读，**不参与自动清理**） | 单文件 | 手动 |
| `data/topics.json` | 转交话题状态（主题 → 根卡片 id；聚合当前未启用，见下文「话题聚合」） | 单文件 | 常驻 |
| `data/history.json` | 本群近期交互（@ 消息、机器人回复，以及全量消息模式下的普通消息） | 单文件，按时间窗自动瘦身 | 常驻（默认留 6 小时） |

- 保留期由 `DATA_RETENTION_DAYS` 控制（默认 30 天）。清理在**启动时**和**每 6 小时**各执行一次，只删除严格匹配上述命名规则且超过保留期的文件，目录里其他文件一律不碰。
- 进程自身的 stdout 日志不写文件；用 docker compose 部署时由 Docker 的 `json-file` 驱动轮换（`max-size 10m` × `max-file 3`，总量封顶 30MB）。
- 旧版本的 `data/forwards.jsonl` 和 `data/raw-events.jsonl` 会在下次启动时**自动归档**到新命名（前者并入当月文件，后者按最后修改时间命名），不会丢数据。
- `data/` 里都是 openid 与用户问题原文，建议 `chmod 700 data`。

## 两个平台的限额

**QQ 开放平台**（官方未公开的数值我标了「未知」）：

- 被动回复：需在收到消息后 5 分钟内回复，同一 `msg_id` 用递增 `msg_seq` 回复多条；**单条 `msg_id` 最多能回复几条官方没有公开**，所以 `REPLY_MAX_CHUNKS` 默认保守取 3。
- 单条文本长度上限：官方未公开（`splitReply` 按 1600 字符分段自保）。
- 主动消息：有额度限制（未认证机器人约 4 条/群/月），本项目全程只用被动回复，不消耗额度。
- 媒体上传：`upload_prepare` 有日额度，命中会报错；图片发送场景要注意。
- 流式消息：仅 C2C 私聊可用，群聊不支持。

**飞书**：

- 频率控制按「每个 API / 每个应用 / 每个租户」分级，发送消息类接口同一群约 **5 QPS**；超限返回 HTTP 429、错误码 `99991400`。
- 自定义机器人是 100 次/分钟、5 次/秒；本项目用的是企业自建应用，走前一条规则。
- 文档未提及每日调用总量上限。

## 转交卡片与话题聚合

推送到飞书反馈群的是一张**折叠卡片**，群里外露的只有一行问题概要：

- 概要由模型按 `用户<昵称>……` 的格式写，例如「用户Heuluck要求修改姓名」；
- 「详情」折叠面板（默认收起）里装着模型写的完整详情，以及诊断信息：截断的用户标识、完整 openid、QQ 消息 id、时间；
- 也就是说群里看到的只有：卡片标题 + 一行概要 + 一个折叠面板。

**话题聚合（当前未启用）**：代码里还留着「同一用户、同一主题的后续补充挂到原卡片下（标题为「🔁 补充 #N」）」这条路径，但**模型拿不到主题标识**——`forward_feedback` 的参数只有 `summary` / `details`，没有 `topic`，所以每条转交都独立开一张卡片。若要启用：

- 在 `src/llm/tools.ts` 的 `ForwardFeedbackArgs` 里加回可选的 `topic`（命中知识库条目时填条目 id，否则用「支付-重复扣费」这类短词），并在知识库提示词里带上条目 id（`src/kb/kb.ts` 的 `renderBlock`）；
- 状态存在 `data/topics.json`：`<用户openid>::<topic>` → 根卡片消息 id、时间、条数。窗口由 `FORWARD_TOPIC_WINDOW_HOURS` 控制（默认 24 小时），超窗视为新主题、新开卡片；
- 判定是**自维护状态**而不是让 AI 现场比对历史消息——这样不需要额外的读消息权限，结果确定、不额外烧 token；
- 如果群聊不支持话题回复（飞书返回 `230071`/`230072`），会自动降级为发新卡片并记一条 warn 日志。
  普通群本来就支持「对一条消息创建话题」（`reply_in_thread: true`），不需要把群设成话题群；
  `230071` 的适用范围官方没写清，实测碰到再处理即可——知识库管理卡片走的是同一套降级逻辑。

## 上下文与图片

**前置设置**：QQ 群里把「机器人可获取的群聊消息范围」设为 **「获取@机器人的最近10条消息」**（群设置 → 机器人）。
只选「仅获取@机器人的消息」的话，机器人只能看到当前这条 @，拿不到上下文。

开启后平台会把最近若干条消息**预渲染成一段文本**，随 @ 事件一起送达（SDK 的 `quoteRef` 中间件解析成 `ctx.state.quote`）。这段文本形如：

```
=== 消息 1 ===
[消息内容]  已经帮主人转交人工啦，正在处理中喵~
=== 消息 2 ===
[附件1] 类型:图片 文件名:xxx.png 尺寸:872x544 大小:292.6KB URL:https://multimedia.nt.qq.com.cn/download?...
```

我们的处理：

- 文本作为「[对话上下文]」附在本轮问题后面（说明里写清它是背景、不是这次要处理的新问题）；
- **图片只以 URL 形式出现在文本里，模型看不见**，所以 `src/qq/context.ts` 会把 URL 抠出来、由 `src/qq/media.ts` 下载并缩放后作为真正的图片附件喂给模型，同时把那段超长 URL 从文本里删掉（省 token）。
- 当前消息自带的附件与上下文里的图片**共享 `IMG_MAX_COUNT` 配额**（默认 2 张，当前消息优先）。常发多图可以调大，代价是每张图约 1k token。

### 上下文渲染成多轮 messages

平台那段文本不可靠（实测纯 @ 消息根本不带，用户看到回复后立刻 @ 一句时平台也常常什么都不给），所以机器人自己维护一份本群交互记录（`data/history.json`），把它渲染成**真正的多轮 `messages`**：

```
[system]  规则 + 知识库（逐字节稳定）
[user]    [16:04] 用户Heuluck: （发了图片）        + 图片
[assistant] 那个旧版包确实是群文件里的，现在最新是 5.16.0……
[user]    [16:06] 用户Luck: 我也有这个问题
[assistant] 你也一样，换成 5.16.0 就行喵~
[user]    问题：已经改好了          ← 最后这条是现在要处理的
[system]  本轮提示：只答最后那条（或那几条）消息里的问题……   ← 固定常量，见「缓存与成本」
```

两个理由，都不是可选的：

1. **图片必须待在它到来时的那一轮。** 把历史拼成一段文本时，翻出来的旧截图只能作为「当前这条消息」的附件交给模型，模型没有依据区分新旧——实测它把 25 分钟前那张崩溃截图当成这次的新证据，回了「看你发的截图还是会弹严重错误崩溃」，并因此**误转交了一次人工**。Anthropic 的 vision 文档给的就是这个模型：图留在原始轮次，模型能看到历史里的所有图，但不要在新增的那一轮里重复贴。
2. **历史成为可缓存的前缀。** 从 system 到历史逐字节稳定、只往后追加，能命中厂商的前缀缓存，只有最新那一轮按原价计费。实测同一个请求打两次，第二次 `缓存命中=3456/3598`。反过来，把整段历史塞进当前那条 user 消息，它每轮都变，缓存全废——**「把历史里的图删掉」看着省 token，实际会让缓存从改动点起整段失效**（OpenAI 与 Anthropic 的缓存文档都写明这一点），删一张图远不够抵消这个代价。

发言人靠**文本前缀** `[HH:mm] 用户<昵称>: ` 区分，不用 messages 的 `name` 字段——实测 DeepSeek 与 GLM 都接受 `name` 却不生效（不报错，也不影响归属判断）。机器人自己的历史轮**不加前缀**：加了它会在给用户的回复里也带上时间戳（实测出现过「[16:12] 好嘞，搞定就行喵~」）。

**会话边界就是「闲置」**：超过 `HISTORY_INJECT_MINUTES`（默认 60 分钟）没说话就当作新会话。这是各家对话平台的通行约定（Dialogflow CX 默认 30 分钟、Rasa 60 分钟、Amazon Lex 5 分钟）。存储窗口另有 6 小时，只影响 `data/history.json` 留多久，不影响喂给模型的内容。

**条数与字符预算是两个上限，超了都从头部整轮丢**：

- `HISTORY_MAX_ENTRIES`（默认 30 轮，一轮 = 一条用户消息或一条机器人的回复）。别的框架的默认量级：LangChain 滑窗记忆 k=5（10 条）、FastGPT 6 轮、LangBot 10 轮、CowAgent 的 agent 模式 30 轮。给小了会出问题——实测 10 条在两人交错的群里只覆盖几分钟，机器人自己刚说过的「先升到 5.16.0」被挤出窗口，于是下一轮又把同一个问题从头答了一遍；
- `CONTEXT_MAX_CHARS`（默认 3000）。**整轮丢弃**而不是切字符串：切开会让「提问」和它的「回答」分家，模型会看到一个没有前因的答复。

`HISTORY_ENABLED=false` 可整体关掉本地缓冲。

### 工具调用也要进历史

机器人的每一次 `forward_feedback` 都会连 **调用 id、参数、执行结果** 一起记进缓冲，下一轮按原样还原成 `assistant(tool_calls)` + `tool` 两条消息：

```
[user]      [16:04] 用户Heuluck: 怎么崩了啊
[assistant] 是 5.14.0 旧版的问题，先换成 5.16.0。这条我已经转给负责的同学了。
            ↑ 这一轮实际上先是 assistant(tool_calls=forward_feedback) → tool(已转交…) → 这条正文
[user]      [16:06] 用户Luck: 我也有这个问题
[assistant] 你也一样，换成 5.16.0 就行喵~
[user]      问题：帮我转人工          ← 本轮
```

**只记回复文本是不够的**：模型看不到自己调用过什么，就会对同一个问题重复转交人工——早期数据里同一个 5.14.0 崩溃确实被转交了两次。加上之后实测：

> 问「上面那个崩溃问题，你已经帮谁转过人工了？」
> 答「只转了一个，用户 Heuluck 那个。你这边先换 5.16.0 试试就行，还崩的话引用我这条再 @ 我，我再帮你转。」

两个实现要点：

- **字段原样保留**（尤其 provider 给的 `id`）。回放时要拼回 `assistant(tool_calls)` + `tool`，id 对不上请求就是非法的；而对得上时，这一轮请求的前缀和上一轮逐字节一致，缓存能继续往后接（实测回放工具轮后 `prompt=2525 缓存命中=2304`）。
- **只记进了 `messages` 的那些调用**。补答（`askForReply`）与「正文形态」解析出来的调用都没进 `messages` 数组，记进缓冲反而会让下一轮前缀和当时对不上，所以不记。代价是这两条兜底路径上的转交，模型下一轮看不到（它们的用户可见回复里本来就写了「已转交」）。

### 一次调用完成：不照抄「调工具 → 回灌 → 再要一次」

一条消息里常常有**两件性质不同的事**：知识库里能直接答的内容，和「已转给负责的同学」这类跟进说明。实测模型在转交时会只顾后者，用户什么答复都拿不到（飞书卡片上还写着「已回复：已告知……」，处理人员会以为用户已经拿到答案了）。

根因是**标准两轮循环本身**：带 `tool_calls` 的 assistant 消息可以带 `content`，那在协议上就是模型说的话（不是草稿），而模型通常**在那一轮就把完整答案写好了**。旧实现只取第二轮当回复——第一轮的答案直接丢掉。实测（复刻一段真实的转交对话，跑 10 次）：

| | |
|---|---|
| 答案写在带 tool_calls 的那一轮 | 9/10 |
| 第二轮重复了答案 | 5/10 |
| 用户最终拿到答案 | **5/10** |

更糟的是第二轮有时写一句**指向上一轮的备注**，用户收到的是「（已在上方回复中说明转交）」。而这也解释了「谎称已回复」：模型认为自己写了就是说过了，所以下一轮它会说「我确实直接答了」（17:06 那次、17:41 飞书卡片那次都是同一件事）。这条缺陷**改动前就存在**（`3700a80` 的循环与旧版逐行相同），用旧提示词+旧请求形状复现，最后一轮带答案的比例是 **0/8**——比现在更差。

**现在的做法：一次调用完成。** 模型在同一条 assistant 消息里既给正文又给 `tool_calls`，正文就是要发出去的那条；代码执行工具，但**不再要第二轮**。于是「答案写在哪个位置」这个问题不存在了——只有一个位置。少一次调用（实测省约一半时间）。

代价是模型写正文时还不知道工具结果，所以提示词要求它把转交说成**将来时**（「我会帮你转给负责的同学」）。工具返回值里那点信息（成功 / 已经转过 / 通道没就绪 / 每小时超限）本来也只有失败路径需要它改口。只有正文为空时才会追加一次请求（`askForReply`）——那时工具结果已经回灌进 `messages`，它能带着结果作答。

实测（同一段历史、跑 10 次）：电费答案 + 神秘商店答案 + 转交说明**三件都齐 9/10**；说成「已转交」的 1/10（提示词要求将来时）；1 次调用 `send_followup` 补了一条。

还留着的另一条：`details` 里**禁止写「已回复」「已告知」**。它对应亲眼见过的假声明，而且这段详情会被记进对话缓冲、回放给模型自己看。

### 补充消息工具（`send_followup`）

让模型在主回复之外再单独发一条消息。

- 每轮**最多调用一次**，在**代码层**拦死（`createTurnTools`）：第二次调用返回一句「已经用过了，这条没有发出」，不发出任何东西。
- 顺序固定：先发主回复，再发补充消息。
- 「正文形态的调用」（模型把调用写成散文）也一并生效——`src/llm/toolmarkup.ts` 是按名字分发的。
- 平台限制落在代码里：官方文档（`tencent-connect/bot-docs` 的 `send.md`）按场景写明，群聊「被动消息（回复类）有效时间为 **5 分钟**，**每个消息最多回复 5 次**」，超时会发送失败（注意 5 分钟是**群聊**的，60 分钟那条是单聊的）。所以主回复分段数 + 补充消息一起卡在 5 条以内（`MAX_PASSIVE_REPLIES`）。

### 什么时候会引用那条 @ 消息

机器人回答需要几秒到几十秒，这期间群里的时间线可能被推进，被动回复就会**飘在那些新消息上面**，群里看不出它在回谁。所以：**从收到这条 @ 消息、到答案生成完毕准备发送，这中间只要有新消息进来，主回复就带上 `message_reference` 引用回那条 @ 消息；没有就不引用。**

- 判断全在**代码**里做（`createArrivalTracker` + `needsQuote`）：每进一条群消息就记一笔，handler 拿着「我这条」的序号在发送前比一次。**模型不参与，也没有让模型手动引用的出口**——引用是平台能力，不该占用提示词、更不该让模型猜。
- **机器人自己发出的消息也算。** 两个人前后脚 @ 机器人时，前一个人的答复先发出去、后一个人的答复就落在机器人的上一条回复下面。平台确实会把机器人自己发的消息回推（`senderIsBot`），但那条被 SDK 的 `messageFilter` 挡在簿记之前——所以不能只数入站事件，代码在**每发出一条群消息之后**补记一笔（`trackOwnMessage`，不依赖回推；发送失败不记，那条没进群）。
- 入站消息的判据是「平台有没有推给我们」：`@机器人`的消息任何设置下都会推，一定算数；**普通消息只在群设置选了「获取群内全部消息」时才会以 `GROUP_MESSAGE_CREATE` 推过来**（选「获取@机器人的最近10条消息」时，平台只是把最近 10 条渲染进 @ 事件的上下文文本，之后进来的普通消息我们收不到，也就无从判断）。
- 每条正文都带引用（不是只有第一段）：群里正热闹的时候，后一段同样可能落到别人消息下面。
- 补充消息（`send_followup`）**不引用**：它是主回复的附注，紧随其后发出。
- 平台拒绝引用时（返回错误）自动退回普通回复并把 warn 打进日志——引用只是为了挂对位置，不能因此把答案吞掉。
- 实现走 `bot.send({ messageReference: { message_id } })`：`sendText` 没有这个参数。两条路径都带 `msg_id`、`msg_seq` 照常生成，所以仍是被动回复，不消耗主动消息额度。
- 日志里能看到这次有没有引用：`回复完成 …｜引用那条@=否`。

### 图片

**四个来源**（按优先级：当前消息附件 → 被引用消息的图片 → 历史轮次里该用户的图片 → 平台上下文文本里的图片）：

1. 当前消息自带的附件（`msg.attachments`），最多 `IMG_MAX_COUNT`（默认 2）张；
2. **被引用消息里的图片**：这是结构化附件（`msg_elements[0].attachments`，SDK 解析到 `quote.attachments`），平台不会把它渲染进上下文文本，必须单独读——否则「引用一张图问这是什么」时模型只能看到 `[图片]` 占位符；
3. **历史轮次里该用户的图片**：按「该用户最近的图」找，而不是按「最近 N 条消息」找——用户连发几张截图后中间常会插入别人的消息，按消息条数回看会把图挤出去（实测踩过）。最多 `IMG_CONTEXT_MAX_COUNT`（默认 5）张，只取**当前 @ 的这个人**自己发的图，挑中的图**挂在它到来的那一轮**上；
4. 平台上下文文本里的图片（形如 `[附件1] 类型:图片 … URL:https://…`），抠出 URL 后下载。平台那段文本拼不出轮次，只能整段当背景，所以它的图紧跟在背景说明之后。

**没有「已答复就不再喂」这类闸门**。图留在自己那一轮，模型能看到历史里的所有图，这是正确行为；要不要参考由模型按时间和上下文判断（系统规则里明确写了「别把几十分钟前的截图当成刚刚发生的新故障」）。我们曾经加过一道「图答复过就不重复注入」的闸门，那是错的：它既让模型在后续追问里看不见图（只能请用户重发，多一整轮交互），又让缓存从改动点失效。

**同一个 URL 只处理一次，处理结果在进程内缓存**（`src/qq/media.ts`，最多 60 张 / 24MB）。历史里的图每轮都要重新交给模型，没有这层缓存就会每轮重新下载 + 缩放。

**下载与解码都有硬上限**：地址必须是 `qq.com` / `qq.com.cn` 的 HTTPS（每一跳重定向都重新校验），字节数上限 `IMG_MAX_BYTES`（默认 10MB），**解码像素上限** `IMG_MAX_PIXELS`（默认 6400 万，交给 libvips 的 `limitInputPixels`）。最后这条是防解压炸弹的：一张 10MB 以内的 PNG 能解到上亿像素、吃掉几百 MB 内存，把容器直接 OOM 掉；超限的图只会被判为「这张图没读到」，不影响其它消息。

**带图的轮次后面跟一个图注**，形如 `[16:06] 用户Heuluck: 怎么崩了啊 ［图：16:06］`。这是 Anthropic vision 文档在多轮场景下的要求：给每张图一个短标签，后续轮次才能按名字引用它。实测没有图注时问「第 1 张、第 2 张分别是什么颜色」会答错甚至数错张数；有了图注，模型能准确列出「16:04 一张、16:06 一张，还有 16:08 那张群聊截图」。用**该轮的时间**而不是「第 N 张」做标签——序号会随窗口滑动而变，时间不会。

**每日读图额度**：同一用户每天最多**新读** `IMG_DAILY_LIMIT_PER_USER`（默认 10）张。额度按**图片本身**扣——同一张图今天只算一张（缓存命中不算，缓存被淘汰后重新下载也不算），否则用户发一张截图聊三句，额度就用完了。额度用完后仍正常回答文字问题，但会在回复里说明今天的图片额度用完、请他文字描述或明天再发；如果本条消息的图其实读到了（是更早的图占了额度），说的就是「新发的图读不到」而不是谎称这条消息的图没读到。日志：

```
回复完成 1180ms｜转交=false｜工具轮 0（无）｜引用那条@=否｜历史 24 轮（历史图 2 张）｜本图 消息 0/0、引用 0/0｜下载 0 张、新计额度 0 张（缓存 2）｜平台背景=false
```

### 回归记录

对真实事故流做过重放（`data/history.json`）：用户 15:38 发报错截图、15:40 问「怎么崩了啊」、15:42 之后话题转到补卡、最后说「已经改好了」。旧结构在最后两轮仍然把那两张 40 多分钟前的截图挂在**当前消息**上；新结构里它们各自待在 `[16:04]`、`[16:06]` 那两轮，当前轮没有任何图，整段 24 轮对话都在。

记录里是用户问题原文，建议 `chmod 700 data`。该文件按时间窗自动瘦身，不属于按天保留的数据文件。

## 缓存与成本

提示词缓存按**逐字节前缀**匹配，所以请求被组织成「稳定前缀 + 只往后追加」：

| 位置 | 内容 | 每次请求 |
|---|---|---|
| 最前 | system 规则 + 知识库 + 工具定义 | 逐字节相同 → 命中缓存 |
| 中间 | 本会话的历史轮次（含当时的图片） | 只追加不改写 → 命中缓存 |
| 最后 | 本次提问（+图片） | 唯一 → 按原价 |
| 末尾 | 一条固定提示（`REPLY_HINT`，见下） | 常量 → 只这点未命中 |

实测同一个请求打两次，第二次 `prompt=3598 缓存命中=3456`——历史（含图）都在缓存里。

**末尾那条固定提示**：请求的最后一条是一条 system 消息，一句话重复本轮最容易违反的规则（`src/llm/messages.ts` 的 `REPLY_HINT`）。它必须是常量，且追加在末尾——缓存是前缀匹配，末尾追加**不碰前面的任何字节**，实测三臂（不加／加在末尾 system／加在末尾 user）命中率都是 94%，只多这 29 token 未命中。

为什么规则要放在末尾：**同一句话，放末尾和写在规则正文里差一个数量级**。用线上真实那一轮（群里已有同学接手的手机号问题 + 一句空 @）配对跑 20 次：写进规则块，重复转交 10/20；放末尾，1/20（p=0.003）。同一批次交替采样，排除了时段漂移。所以以后遇到「规则写了模型不听」，先把它挪到末尾，而不是继续改措辞或加长正文。

失效有三种情况：改知识库、改系统规则、改工具定义（都发生在发版时刻，属于主动失效）；以及历史窗口滑动，从头部丢掉最老的一轮——这是唯一会周期性发生的失效，窗口给大一点（默认 30 轮）就能让它很少发生。

> 这也是**不要给历史做「删减式」优化**的原因：把某张旧图从历史里删掉、或把几轮历史压成摘要，都会让缓存从改动点起整段失效并按原价重算（OpenAI 与 Anthropic 的缓存文档都明确写了）。要省，就从头部整段丢，别从中间改。

日志里能看到命中情况（`[llm] tokens prompt=... （缓存命中=...）`）。DeepSeek 命中价约为未命中的 1/10，GLM 的隐式前缀缓存同样免费命中。

**思考档位默认关闭**（`LLM_REASONING_EFFORT=none`），这不是省钱，是防「正文被推理挤空」：推理内容**计入 `LLM_MAX_TOKENS`**，实测让 `deepseek-flash` 读一张报错截图，reasoning 会把 1024 的全部预算吃光，返回 `finish_reason=length` 且 `content` 为空——于是走 `askForReply` 再要一次，而兜底用的是同一个预算，可能再空一次。关掉之后同一张图 1.3 秒出结果、只花 88 token（原来 4.8 秒且答不出来），工具调用与读图准确度实测不受影响。

| 端点 | 关思考 | 说明 |
|---|---|---|
| DeepSeek | `LLM_REASONING_EFFORT=none` | 也可填 `minimal` / `low` / `medium` / `high` / `max` |
| GLM | 只能填 `low`（关不掉） | 填 `none` 会 400「该模型始终思考」；`low` 的 reasoning 从约 1k 字符降到约 100，效果接近关掉 |
| 其他 | 填 `default` 表示不带这个参数、用厂商默认值 | |

## 排错

| 现象 | 原因与处理 |
|---|---|
| 启动报「仍是占位符」 | `.env` 里有 `PASTE_` 没替换 |
| 启动报「机器人不在任何飞书群里」 | 先把机器人拉进反馈群，或手动填 `LARK_FEEDBACK_CHAT_ID` |
| 启动报「机器人所在群不唯一」 | 日志里会列出所有群与 chat_id，挑一个填进 `.env` |
| 群里 @机器人没反应 | 看日志有没有「收到群消息」；若 `QQ_GROUP_OPENID` 填错了会被静默忽略 |
| 想换模型 | 改 `.env` 的 `LLM_BASE_URL` / `LLM_MODEL`（DeepSeek 与 GLM 都支持多模态与工具调用）；换 GLM 时记得把 `LLM_REASONING_EFFORT` 改成 `low`，它关不掉思考 |
| 回复偶尔是空的兜底文案（「我暂时没找到答案」） | 多半是推理吃光了 `LLM_MAX_TOKENS`。确认 `LLM_REASONING_EFFORT=none`，或把 `LLM_MAX_TOKENS` 提到 2048 以上 |
| 转交没到飞书 | 看日志 `[fwd]`；检查是否触发限频（同一用户每小时上限，默认 5 次） |
| 群里 @机器人 不弹知识库菜单 | 日志 `[kb-admin]` 会说实话：①「忽略非白名单成员」→ 把那个 `open_id` 加进 `LARK_ADMIN_OPEN_IDS`；② 完全没有 `[kb-admin]` 日志 → 开发者后台的「事件订阅」没切成**使用长连接**或没订阅 `im.message.receive_v1`；③「长连接建立失败」→ 检查 AppID 格式与网络出站 |
| 点了卡片按钮弹「回传数据签名不匹配」 | 换过 `LARK_APP_SECRET`，旧卡片上的签名随之失效；重新 @机器人 拿一张新卡片即可 |
| 卡片按钮点了没反应 / 客户端提示超时 | 回调必须在 **3 秒内**响应；看日志有没有 `[kb-admin] 处理 … 失败`。另外飞书客户端太旧会不支持表单容器（约需 V6.6+） |
| 知识库卡片刷屏了 | 说明这个群不支持话题回复（日志有 `230071`），卡片降级成了直接发在群里。换个支持话题的群，或接受这个降级 |
| 想让反馈群里所有人都能加知识库 | `.env` 里 `LARK_ADMIN_OPEN_IDS=*`，**且必须**同时设 `LARK_FEEDBACK_CHAT_ID`；少配一样就只在启动日志留一条 warn、谁都用不了 |
| 飞书新增条目被拒 | 卡片上会写原因：`id` 与正式知识库撞车 / 答案超 1000 字 / 飞书层超 `KB_FEISHU_MAX_CHARS` / 合并后超 `KB_MAX_PROMPT_CHARS` |

## 设计取舍

- **上下文靠自维护的缓冲，不依赖平台**：平台那段「最近 N 条消息」并不可靠（纯 @ 消息根本不带），所以机器人自己记一份本群交互（含**自己发过的回复**），渲染成多轮 `messages` 当作请求前缀。这样图片能待在它到来时的那一轮，历史也能命中前缀缓存——详见上文「上下文与图片」。
- **同群串行处理**：上下文是同群共享的可变状态，「读历史 → 调模型 → 写回复」这一整段不能被别的消息插进来，否则会读到「有问题、还没答复」的中间态，历史错乱后模型会把自己的上一轮回答当成新问题（中文社区有同构的踩坑记录）。CowAgent 的默认也是这个语义（`concurrency_in_session: 1`）。代价是同群第二条消息要排队等前一条跑完。
- **不做上下文摘要压缩**：Anthropic 的 compaction、Claude Code 的 `/compact` 都靠摘要来支持超长会话，但摘要会改写前缀、让缓存失效，而这个场景的会话很短（闲置 1 小时就重置），滑窗整轮丢弃已经够用。
- **飞书只做提醒，外加一个知识库管理入口**：转交侧不建工单、不做状态流转，人工在群里线下处理。飞书唯一会「收」的是**管理员 @机器人** 和**卡片按钮回调**，都走同一条长连接；机器人不看群里其它聊天（权限只申请了 `im.message.group_at_msg:readonly`）。
- **知识库分两层、两套写路径**：`kb.feishu.yaml` 由飞书菜单写、改文档走 schema 重渲染、热重载；`kb.yaml` 是人工维护的主文件，飞书那条路径改不到它，要走主菜单里单独的**红色危险入口**（二次确认 + 填提交说明 + 回收站 + `git commit`）。两者在代码上是独立入口——补充层**结构上够不到**基线文件，比「靠校验拦住」更省心；正式库的改动则靠「确认 + 回收站 + git」三重兜底，且注释由 `parseDocument` 原样保留。转正到正式库仍是一次明确的动作，不做静默提升。
- **单一写操作工具**：只有 `forward_feedback`（zod 校验 + 按消息幂等 + 按用户限频）。工具框架在 `src/llm/tools.ts`，加工具只需补一个定义与执行分支。每次调用都会连 id、参数、结果记进对话缓冲，下一轮模型看得到自己转过谁（见上文「工具调用也要进历史」）。
- **工具调用可能写成正文**：`deepseek-flash` 这类模型有时不返回结构化 `tool_calls`，而是把调用写进正文（原生 `<||DSML||…>` 标记，或散文式的一行）。`src/llm/toolmarkup.ts` 会把这种调用解析出来**真的执行**，并把标记从给用户的回复里剔除——否则会出现「说已转交但其实没转交」，同时把内部信息（知识库条目、转交说明）发到群里。日志出现 `模型把工具调用写成了正文，已解析并执行` 就是这个情况。
