# incu-qq-bot

QQ 群客服机器人：官方 SDK 收 `@机器人` 消息（含被引用的消息与图片），用 OAI 兼容模型 + 知识库作答；答不上来的转交到飞书反馈群提醒人工。

**全程无公网暴露**：QQ 走官方 WebSocket 网关，飞书只调发消息 API，进程不监听任何端口。

## 架构

```
QQ 群（用户群）                                飞书（反馈群）
  用户 @机器人 + 可选引用/图片
        │
        ▼
  @tencent-connect/qqbot-nodejs（WS 长连接）
        │  中间件：去重 → 去 @标记 → 必须@ → 限流 → 引用解析
        ▼
  ┌─────────────────────────────────────────┐
  │ 一次模型调用 = 静态前缀 + 单条动态消息      │
  │   [system] 规则 + 知识库（逐字节稳定）      │
  │   [user]   本次提问 + 图片(data URL)      │
  └─────────────────────────────────────────┘
        │
        ├── 知识库命中「可直接回复」→ 被动回复用户
        └── 需转交 → 调 forward_feedback 工具
                        │
                        ├── 回复用户「已转交，正在处理中」
                        └── 飞书 REST 推送提醒卡片 ──► 反馈群（只发不收）

  数据落盘：data/forwards-YYYY-MM.jsonl（转交记录，按月切分，保留 30 天）
```

## 快速开始

### 1. 填凭据

复制 `.env.example` 为 `.env`（仓库里已给好 `.env`，内容一致），把 `PASTE_` 占位符换成真实值。程序只列出缺哪些变量，永远不会打印凭据内容。

```bash
# 先不填 QQ_GROUP_OPENID 也能跑：机器人会把看到的群 openid 打进日志
grep "收到群消息" <日志>   # 复制 group=oc... / group=... 那个值填回去
```

### 2. 本地运行

```bash
fnm use 24        # 需要 Node >= 24
npm install
npm run smoke     # 离线自检（不需要凭据）
npm run dev       # 开发模式，改代码自动重启
```

### 3. 服务器运行（Docker）

```bash
docker compose up -d --build
docker compose logs -f      # 看日志
docker compose restart      # 改完 kb/kb.yaml 后重启生效
```

`docker-compose.yml` 里没有 `ports:`，只走出站连接；内存上限 320MB。

## 需要开通的权限

### QQ 开放平台（[q.qq.com](https://q.qq.com)）

1. 创建机器人应用，在「开发设置」拿到 **AppID / AppSecret**。
2. 群聊能力开箱即用，**不需要**申请全量消息、**不需要** markdown 报备、**不需要**配置回调地址（本机器人用 WebSocket 长连接）。
3. 把机器人拉进用户群。
4. 只有 `@机器人` 的消息会到达机器人，引用消息的内容会随事件一起送达（这是官方支持的能力）。

### 飞书（[open.feishu.cn](https://open.feishu.cn) → 开发者后台）

1. **创建企业自建应用**，拿到 **AppID / AppSecret**。
2. 「添加应用能力」→ 开启 **机器人**。
3. 「权限管理」开通这两个权限（只需要这两个）：
   - `im:message:send_as_bot` —— 以应用身份发消息（推送转交卡片）
   - `im:chat:readonly` —— 获取机器人所在的群列表（启动时自动识别反馈群）
4. 「版本管理与发布」创建版本并发布（企业自建应用按你的组织流程走审批）。
5. 把机器人拉进**反馈群**。

> 不需要事件订阅、不需要配置回调地址、不需要卡片回调权限——飞书侧只发不收。

## 知识库

编辑 `kb/kb.yaml`，整体编译进 system prompt（改动后重启进程生效，并让模型缓存按设计失效一次）。

```yaml
entries:
  - id: reset-password          # 唯一 id
    title: 忘记密码 / 无法登录     # 给模型看的条目标题
    keywords: [密码, 忘记密码]    # 触发关键词
    route: answer               # answer=可直接回复 | forward=需转交人工 | answer_and_forward=先回复再转交
    answer: |                   # route=answer 时必须写
      请在登录页点击「忘记密码」……
  - id: billing-refund
    title: 退款 / 订单异常
    keywords: [退款, 订单]
    route: forward
    forward_hint: |             # 建议写：告诉模型转交时要带上什么信息
      需要用户提供：下单账号、订单号、支付截图。
```

规模建议 2000 字以内（约 3k token）。超过 8000 字符启动时会告警。

三种处理方式：

- `answer`：直接回复用户，不建工单；
- `forward`：只转交人工；
- `answer_and_forward`：**先回复用户，同时转交人工**——适合「用户能自助办、但可能需要人工兜底」的场景（例如修改手机号：旧号还能用就自助改，不能用了得人工处理）。这类条目每次命中都会同时给用户答复并建一张转交卡片。

## 限额与截断

| 环节 | 默认值 | 环境变量 |
|---|---|---|
| 用户单条提问 | 超过 4000 字符截断并标注 | `QUESTION_MAX_CHARS` |
| 上下文整段 | 超过 3000 字符时保留最新的部分 | `CONTEXT_MAX_CHARS` |
| 上下文单条消息 | 超过 600 字符单独截断（防一条超长粘贴挤掉其他） | `CONTEXT_MESSAGE_MAX_CHARS` |
| 回复发送 | 每段 ≤1600 字符、最多 3 段，超出截断 | `REPLY_MAX_CHUNKS` |
| 分钟级 | 单用户 6 条/分钟、单群 40 条/分钟 | `RATE_LIMIT_PER_MINUTE` / `RATE_LIMIT_PER_GROUP_PER_MINUTE` |
| 每日 | 单用户 10 条/日、全机器人 100 条/日 | `REPLY_LIMIT_PER_USER_PER_DAY` / `REPLY_LIMIT_GLOBAL_PER_DAY` |
| 转交 | 单用户 5 次/小时（计入上面同一份每日额度） | `FORWARD_LIMIT_PER_HOUR` |

- 计数按**东八区自然日**统计，落盘 `data/limits.json`，重启不清零；跨日自动重置并把前一天的用量归档为 `limits.YYYY-MM-DD.json`。
- 命中限额时只回一句提示，且**同一用户每分钟最多提示一次**（避免提示本身刷屏），不再调用模型。
- **豁免名单**：`PRIVILEGED_USERS`（逗号分隔 openid）里的用户不受分钟级、群级、转交每小时的限制，每日额度用 `PRIVILEGED_LIMIT_PER_DAY`（默认 100）。全局限额对他们仍然生效。
- 转交不单设每日上限，它和普通回复共用同一份「用户每日额度」。

## 数据文件与保留

| 文件 | 内容 | 切分方式 | 保留 |
|---|---|---|---|
| `data/limits.json` | 当日配额（openid → 次数、全局次数） | 单文件，跨日重置 | 常驻 |
| `data/limits.YYYY-MM-DD.json` | 每天的用量归档 | 每天一份 | 30 天 |
| `data/forwards-YYYY-MM.jsonl` | 转交留档（问题、详情、话题、飞书消息 id） | 按月切分 | 30 天 |
| `data/raw-events.<时间戳>.jsonl` | debug 原始事件转储 | 每次调试会话一份 | 30 天 |
| `data/topics.json` | 话题聚合状态（主题 → 根卡片 id） | 单文件 | 常驻 |
| `data/history.json` | 本群近期交互（@ 消息、机器人回复，以及全量消息模式下的普通消息） | 单文件，按时间窗自动瘦身 | 常驻（默认留 6 小时） |

- 保留期由 `DATA_RETENTION_DAYS` 控制（默认 30 天）。清理在**启动时**和**每 6 小时**各执行一次，只删除严格匹配上述命名规则且超过保留期的文件，目录里其他文件一律不碰。
- 进程自身的 stdout 日志不写文件；用 docker compose 部署时由 Docker 的 `json-file` 驱动轮换（`max-size 10m` × `max-file 3`，总量封顶 30MB）。
- 旧版本的 `data/forwards.jsonl` 和 `data/raw-events.jsonl` 会在下次启动时**自动归档**到新命名（前者并入当月文件，后者按最后修改时间命名），不会丢数据。
- `data/` 里都是 openid 与用户问题原文，建议 `chmod 700 data`。

## 两个平台的限额

**QQ 开放平台**（官方未公开的数值我标了「未知」）：

- 被动回复：需在收到消息后 5 分钟内回复，同一 `msg_id` 用递增 `msg_seq` 回复多条；**单条 `msg_id` 最多能回复几条官方没有公开**，所以 `REPLY_MAX_CHUNKS` 默认保守取 3。
- 单条文本长度上限：官方未公开（`splitReply` 按 1600 字符分段自保）。
- 主动消息：有额度限制（未认证机器人约 4 条/群/月），本项目全程只用被动回复，不消耗额度。
- 媒体上传：`upload_prepare` 有日额度，命中会报错；图片发送场景要注意。
- 流式消息：仅 C2C 私聊可用，群聊不支持。

**飞书**：

- 频率控制按「每个 API / 每个应用 / 每个租户」分级，发送消息类接口同一群约 **5 QPS**；超限返回 HTTP 429、错误码 `99991400`。
- 自定义机器人是 100 次/分钟、5 次/秒；本项目用的是企业自建应用，走前一条规则。
- 文档未提及每日调用总量上限。

## 转交卡片与话题聚合

推送到飞书反馈群的是一张**折叠卡片**，群里外露的只有一行问题概要：

- 概要由模型按 `用户<昵称>……` 的格式写，例如「用户Heuluck要求修改姓名」；
- 「详情」折叠面板（默认收起）里装着模型写的完整详情，以及诊断信息：截断的用户标识、完整 openid、QQ 消息 id、时间；
- 也就是说群里看到的只有：卡片标题 + 一行概要 + 一个折叠面板。

**话题聚合**：同一用户、同一主题的后续补充不会新开卡片，而是以**话题回复**挂在原始卡片下（标题为「🔁 补充 #N」）。

- 主题标识由模型在工具参数 `topic` 里给出：命中知识库条目时填条目 id（知识库标题后会带 `（id: xxx）`），否则用「支付-重复扣费」这类短词。
- 状态存在 `data/topics.json`：`<用户openid>::<topic>` → 根卡片消息 id、时间、条数。窗口由 `FORWARD_TOPIC_WINDOW_HOURS` 控制（默认 24 小时），超窗视为新主题、新开卡片。
- 判定是**自维护状态**而不是让 AI 现场比对历史消息——这样不需要额外的读消息权限，结果确定、不额外烧 token。
- 如果群聊不支持话题回复（飞书返回 `230071`/`230072`），会自动降级为发新卡片并记一条 warn 日志；把群设为**话题群**可启用话题能力。

## 上下文与图片

**前置设置**：QQ 群里把「机器人可获取的群聊消息范围」设为 **「获取@机器人的最近10条消息」**（群设置 → 机器人）。
只选「仅获取@机器人的消息」的话，机器人只能看到当前这条 @，拿不到上下文。

开启后平台会把最近若干条消息**预渲染成一段文本**，随 @ 事件一起送达（SDK 的 `quoteRef` 中间件解析成 `ctx.state.quote`）。这段文本形如：

```
=== 消息 1 ===
[消息内容]  已经帮主人转交人工啦，正在处理中喵~
=== 消息 2 ===
[附件1] 类型:图片 文件名:xxx.png 尺寸:872x544 大小:292.6KB URL:https://multimedia.nt.qq.com.cn/download?...
```

我们的处理：

- 文本作为「[对话上下文]」注入到本轮提问里（系统规则里说明它是背景，不得当成新问题回答）；
- **图片只以 URL 形式出现在文本里，模型看不见**，所以 `src/context.ts` 会把 URL 抠出来、由 `src/media.ts` 下载并缩放后作为真正的图片附件喂给模型，同时把那段超长 URL 从文本里删掉（省 token）。
- 当前消息自带的附件与上下文里的图片**共享 `IMG_MAX_COUNT` 配额**（默认 2 张，当前消息优先）。常发多图可以调大，代价是每张图约 1k token。

上下文越长，动态部分的 token 越贵（它位于静态前缀之后，按原价计费），但换来的是能正确理解「这个」「刚才那个」这类指代。

**图片的四个来源**（按优先级：当前消息附件 → 被引用消息的图片 → 对话缓冲里该用户的近期图片 → 平台上下文文本里的图片）：

1. 当前消息自带的附件（`msg.attachments`），最多 `IMG_MAX_COUNT`（默认 2）张；
2. **被引用消息里的图片**：这是结构化附件（`msg_elements[0].attachments`，SDK 解析到 `quote.attachments`），平台不会把它渲染进上下文文本，必须单独读——否则「引用一张图问这是什么」时模型只能看到 `[图片]` 占位符；
3. **对话缓冲里该用户发的近期图片**：按「该用户最近的图」找，而不是按「最近 N 条消息」找——用户连发几张截图后中间常会插入别人的消息，按消息条数回看会把图挤出去（实测踩过）。最多 `IMG_CONTEXT_MAX_COUNT`（默认 5）张，只取**当前 @ 的这个人**自己发的图；
4. 平台上下文文本里的图片（形如 `[附件1] 类型:图片 … URL:https://…`），抠出 URL 后下载。

同一个 URL 只读一次（多个来源可能有同一张图）。**每日读图额度**：同一用户每天最多读 `IMG_DAILY_LIMIT_PER_USER`（默认 10）张，超出后机器人仍正常回答文字问题，但会在回复里说明今天的图片额度用完、请他文字描述或明天再发。日志里分别显示各来源命中张数：
`图片=3（消息附件 0/0，引用 0/0，缓冲 3，上下文 0/0）`。

**平台上下文不可靠，所以有本地兜底**：实测平台并不总是附带那段上下文（例如用户看到机器人回复后立刻 @ 一句，平台可能什么都不带）。
因此机器人自己维护一份本群的近期交互记录（`data/history.json`），记「用户 @ 消息」「机器人回复」，**并且在平台投递全量消息时把群里的普通消息也记上**（群设置选「获取群内全部消息」后，非 @ 消息会以 `GROUP_MESSAGE_CREATE` 事件到达，机器人不回复它们，但会记进缓冲——这样用户随后 @ 一句「这个怎么办」才接得上）：

- 平台给了上下文 → 用平台的（它还能看到非 @ 消息和图片）；
- 平台没给 → 用本地记录，格式为 `[21:34] 用户Heuluck: 没用了` / `[21:34] 客服: …`；
- 日志里明确写出本轮用的是哪个：`本轮上下文：412 字符，来源=本地缓冲`；
- 默认保留最近 **6 小时**；缓冲区最多**存 50 条**、每次**注入 10 条**——存储与注入是两个独立上限，`HISTORY_MAX_ENTRIES`（注入）调大时不用改存储；`HISTORY_ENABLED=false` 可整体关掉。

记录里是用户问题原文，建议 `chmod 700 data`。该文件按时间窗自动瘦身，不属于按天保留的数据文件。

## 诊断

`LOG_LEVEL=debug` 启动后，平台推送的原始事件会落到 `data/raw-events.<时间戳>.jsonl`（每次调试一个文件、单个会话上限 500 条），包含每条群消息的完整载荷、被 mentionGate 拦下的非 @ 消息、以及 SDK 未内部处理的网关事件。排查「平台到底推了什么」时很有用：

```bash
LOG_LEVEL=debug npm run dev    # 每次启动都会新开一个转储文件，无需手动清理
```

## 缓存与成本

提示词缓存按**逐字节前缀**匹配，所以请求被刻意组织成「静态前缀 + 单个动态消息」：

| 位置 | 内容 | 每次请求 |
|---|---|---|
| 最前 | system 规则 + 知识库 + 工具定义 | 逐字节相同 → 命中缓存 |
| 最后 | 本次提问（+图片） | 唯一 → 按原价 |

只有三种情况会让前缀失效：改知识库、改系统规则、改工具定义——三者都发生在发版时刻，属于主动失效。

日志里能看到命中情况（`[llm] tokens prompt=... （缓存命中=...）`）。DeepSeek 命中价约为未命中的 1/10，GLM 的隐式前缀缓存同样免费命中。

## 排错

| 现象 | 原因与处理 |
|---|---|
| 启动报「仍是占位符」 | `.env` 里有 `PASTE_` 没替换 |
| 启动报「机器人不在任何飞书群里」 | 先把机器人拉进反馈群，或手动填 `LARK_FEEDBACK_CHAT_ID` |
| 启动报「机器人所在群不唯一」 | 日志里会列出所有群与 chat_id，挑一个填进 `.env` |
| 群里 @机器人没反应 | 看日志有没有「收到群消息」；若 `QQ_GROUP_OPENID` 填错了会被静默忽略 |
| 想换模型 | 改 `.env` 的 `LLM_BASE_URL` / `LLM_MODEL`（DeepSeek 与 GLM 都支持多模态与工具调用） |
| 转交没到飞书 | 看日志 `[fwd]`；检查是否触发限频（同一用户每小时上限，默认 5 次） |

## 设计取舍

- **不维护对话历史**：QQ 群只投递 `@机器人` 的消息，机器人自己的回复不进上下文。每次请求相互独立，换来的是 100% 稳定的缓存前缀与极简实现。
- **飞书只做提醒**：不建工单、不收飞书消息、不做状态流转，人工在群里线下处理。
- **单一写操作工具**：只有 `forward_feedback`（zod 校验 + 按消息幂等 + 按用户限频）。工具框架在 `src/tools.ts`，加工具只需补一个定义与执行分支。
- **工具调用可能写成正文**：`deepseek-flash` 这类模型有时不返回结构化 `tool_calls`，而是把调用写进正文（原生 `<||DSML||…>` 标记，或散文式的一行）。`src/toolmarkup.ts` 会把这种调用解析出来**真的执行**，并把标记从给用户的回复里剔除——否则会出现「说已转交但其实没转交」，同时把内部信息（知识库条目、转交说明）发到群里。日志出现 `模型把工具调用写成了正文，已解析并执行` 就是这个情况。
